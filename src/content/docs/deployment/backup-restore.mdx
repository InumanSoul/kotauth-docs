Kotauth can export entire workspaces as encrypted, portable archive files that can be imported into another Kotauth instance.

## What a backup carries

| Carried | Not carried |
|---|---|
| Users, including each user's `sub` (since v1.31.0) | Client secrets |
| Roles, groups, user attributes, claim mappers | Identity-provider client secrets |
| Applications, with grant types, audience, launcher settings and token lifetime | The SMTP password |
| Resource servers, client authorizations and per-client scope allowlists | MFA (TOTP) seeds |
| Identity providers: issuer, endpoints, scopes and JIT settings | Signing keys, unless you opt in at export |
| Workspace settings, including its [public domain](/deployment/custom-domains/) | |
| Audit log | |

Restored identity providers stay **disabled** until you enter their client secret again, so a provider without a secret fails at configuration time rather than at the first sign-in. Users with MFA enroll again.

## What import does

- **Signing key.** A backup without signing keys gets a fresh RS256 key in the same transaction that creates the workspace, so it issues tokens right away. A backup that carries its own active key keeps that key.
- **`sub` is preserved.** Relying parties keep every link after a move. Users from a backup taken before v1.31.0 get a new `sub`; the import summary reports how many as `usersWithNewSubject`, and those users must be relinked by `sub`.
- **Legacy usernames are rewritten.** Usernames from backups older than v1.24.0 that break the current format are rewritten, and the summary lists each one with the user's email.
- **Conflicts are refused.** Import fails, changing nothing, when two users in the backup share a `sub`, or a username equals another user's email address.

## Use cases

- **Disaster recovery** — maintain encrypted backups of production workspaces
- **Environment promotion** — export from staging, import to production
- **Migration** — move a workspace between Kotauth instances
- **Testing** — snapshot a workspace before running destructive tests, restore afterward

## Archive format

Exports use the `bkp1` envelope format — a self-contained binary file containing:

| Section | Content |
|---|---|
| Magic bytes | Format identifier (`bkp1`) |
| Metadata | Schema version, tenant slug, export timestamp |
| Salt | 32-byte random salt for key derivation |
| IV | 12-byte initialization vector for AES-GCM |
| Ciphertext | AES-256-GCM encrypted tenant data |

Key derivation uses PBKDF2 with 600,000 iterations and the user-provided passphrase. The high iteration count ensures brute-force resistance even if the archive file is leaked.

:::caution
Archive files are encrypted at rest, but you should still store them in a secure location. The passphrase is the only barrier to decryption — use a strong, unique passphrase and store it in a secrets manager.
:::

## CLI usage

Export a workspace:

```bash
java -jar kauth.jar cli export-tenant \
  --slug=my-workspace \
  --output=/backups/my-workspace-2026-05-01.bkp1 \
  --passphrase="your-strong-passphrase"
```

With Docker Compose:

```bash
docker compose exec kauth java -jar kauth.jar cli export-tenant \
  --slug=my-workspace \
  --output=/data/backups/my-workspace.bkp1 \
  --passphrase="your-strong-passphrase"
```

Import a workspace:

```bash
java -jar kauth.jar cli import-tenant \
  --input=/backups/my-workspace-2026-05-01.bkp1 \
  --passphrase="your-strong-passphrase"
```

See [CLI Commands](/deployment/cli/) for full option reference.

## Admin API

The same operations are available via the REST API for programmatic backup workflows.

### Export

```
POST /admin/api/v1/tenants/{slug}/export
Content-Type: application/json
Authorization: Bearer {admin-api-key}

{
  "passphrase": "your-strong-passphrase"
}
```

Returns the encrypted `.bkp1` archive as a binary download (`application/octet-stream`).

### Import

```
POST /admin/api/v1/tenants/import
Content-Type: multipart/form-data
Authorization: Bearer {admin-api-key}

file: <archive.bkp1>
passphrase: your-strong-passphrase
```

Returns the import summary on success: the new workspace slug and counts of `users`, `applications`, `roles`, `groups`, `claimMappers`, `socialProviders`, `resourceServers`, `signingKeys` and `auditEvents`, plus `usernameRewrites` and `usersWithNewSubject`.

## Schema compatibility

Each archive records the database schema version at the time of export. On import, Kotauth checks that the target instance has run at least that migration version. This prevents data corruption from missing columns or tables.

| Scenario | Result |
|---|---|
| Same schema version | Import succeeds |
| Target is newer (has more migrations) | Import succeeds — additional columns use defaults |
| Target is older (missing migrations) | Import fails with schema mismatch error |
